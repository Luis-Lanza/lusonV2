## Scope and invariants
- Pending cancellation writes no inventory; Approved cancellation releases only this request's active reservations. Physical existing stock and independent holds remain unchanged.
- Server-derived cancellation location/time, immutable original request and optional original approval metadata. Cancelled Pending must not fabricate approval; cancelled Approved preserves it.
- Keep allocation history: `released_at` is distinct from dispatch `consumed_at`; active ownership requires neither marker. Never delete allocation rows or mislabel release as dispatch.
- Reuse integrity-lock/request-lock ordering, sorted balance locks, participant privacy, strict HTTP framing and commit-only invalidations. Duplicate cancellation is a read-only persisted outcome; approve/cancel and dispatch/cancel races preserve a single valid serialized lifecycle.
- Cancelled is terminal, absent from required-action counts. Reads/filter/creation replay, explicit cancellation recovery and approval/dispatch recovery must accept current cancellation truth without claiming approval/dispatch succeeded.
- Controller-owned uncertainty recovery: explicit GET versus identical POST retry, no silent replay, owner/session/token fences and request-scoped privacy masks. Pending/Approved GET alone does not prove a failed POST. Latest Cancelled outranks cached approval.
- Refresh transfer/count lanes on confirmed cancellation; inventory/source only for released Approved reservations.
- Exclude cancellation after dispatch, editing, direct warehouse creation, discrepancy resolution, unrelated UI polish, dependency/config/test fixture changes and prior migration edits.
