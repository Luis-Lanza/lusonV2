# Remove legacy audit flows and unexpected receipt variants

Objective: make unexpected receipt variants impossible by construction and remove the three legacy audit flows (count, restitution, dispatch) from the product, keeping their parsers, SQL readers and tables as historical evidence for the unified snapshot.

Branch: `feat/transfer-unified-delivery`
Delivery strategy: `single-pr` (no PR opened; user asked to hold it)

Delivery slices already committed on this branch:
- `8e8ad9d` feat(api): enforce the receipt quantity floor and retire legacy audit endpoints — 51 files, +927/-3043. API half: S1, S3, S6 routes, S7 contract and every fixture conversion.
- next: feat(web) — S2, S4, S5 and the four-reason client.
- next: docs — this document.

Slice boundaries are recorded here because the combined change is far past the ~400-line review slice, so the single PR must be reviewed slice by slice.
Test runner: `npm --prefix apps/web test` and `go test ./...` from `apps/api`

## Specs

- **S1** The receipt API rejects every line whose `variant_id` is not in the transfer request items. `expected_quantity == 0` receipt lines can no longer be created.
- **S2** The receipt UI offers no way to add a catalog variant that was not dispatched. The "Elegir variante del catálogo" picker and the "Agregar variante inesperada" button are removed.
- **S3** The database enforces `expected_quantity > 0` on `transfer_receipt_lines`. Before adding the constraint, verify no existing row has `expected_quantity = 0`; if any exist, use `NOT VALID`, decide their disposition, then validate. Decision 2026-11-03: production is unreachable, so the migration decides the shape at apply time — validated when the table is clean, `NOT VALID` when historical zero rows exist. No deploy is aborted by historical data and no history is deleted.
- **S4** The "Gestiones" menu no longer lists count, restitution or dispatch audit entries. When only unified remains, the menu is replaced by a direct "Resolver diferencia" action.
- **S5** The legacy audit UI components, hooks, CSS and their tests are deleted. The legacy parsers (`transferCountCorrectionModel`, `transferRestitutionModel`, `transferDispatchReconciliationModel`) and recovery utilities that the unified flow imports stay.
- **S6** The legacy HTTP routes and public store mutation methods are removed. `countSnapshotSQL`, `restitutionSnapshotSQL`, `dispatchReconciliationSnapshotSQL`, `normalizeCountSnapshot`, `normalizeDispatchSnapshot` and `decodeRestitutionHistory` stay because `unified_reconciliation_store.go` reads historical evidence through them.
- **S7** The pending-review categories `review_count`, `review_restitution` and `review_dispatch_reconciliation` are removed from the pending list/count contract. The only consumer is the web app in this repository.
- **S8** Legacy tables and triggers are not dropped. The retirement blocker keeps referencing them so any historical pending proposal still blocks retirement until rejected.
- **S9** All checks pass except the known preexisting failure in `transferUnifiedReconciliationSeam.test.ts` (requires `LUSON_UNIFIED_SEAM_STDOUT`).
- **S10** An administrative recovery command unblocks a transfer stuck in `in_transit` because a physically received variant was never dispatched: it records the event as audit-only evidence, never credits stock automatically, and moves the transfer to `received`. It is a CLI operation, not a UI flow and not a general inventory adjustment.
